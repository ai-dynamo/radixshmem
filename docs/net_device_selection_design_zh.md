# 网络设备发现与选择设计

状态：第 1–4 步已实现（分支 `feat/net-device-discovery`，基线 `feat/pd-support@e98f4be`）：`net_discovery` 模块与 `test_net_select`、服务端/客户端/Python 启动前解析、Mooncake/NIXL 采用诊断、`register_store` 按页所在 NUMA 注册。第 5 步双机验证未做。Mooncake 行为分析参考本地 `v0.3.14` 源码。

## 1. 问题

radixshmem 有三条平面，各自用不同参数选网卡，彼此没有统一的发现、配置解析和诊断入口：

| 平面 | 走什么 | 现有配置 | 留空时的行为 |
|---|---|---|---|
| 控制面：gRPC remote-op、XRC 握手地址发布 | TCP/IP | `rpc_interface` 或 `rpc_address` | 分布式模式报错，必须手填 |
| 索引面：RHT 分片读写、peer-index remote walk | RDMA（XRC/DC） | `index_dev` + `gid_idx` | 取 verbs 枚举的第 0 个设备；GID 默认 3；端口固定 1 |
| 数据面：KV block 搬运 | Mooncake/NIXL，按协议使用 RDMA 或 TCP | `transfer_dev` + `transfer_ip` | 设备由后端发现；握手地址继承控制地址，缺失时 Python 路径可能退到 loopback |

etcd 请求的出接口由操作系统路由决定；`rpc_interface` 当前主要影响地址解析和发布，不会自动把 etcd TCP 连接绑定到该接口。

现状的缺陷：

1. 索引面自动取第 0 个设备，没有先筛选可访问、端口 ACTIVE、GID 有效的候选；多 rail 环境容易选到不适合本次部署的网络。
2. `gid_idx = 3` 是本机常见布局，其他驱动、接口和地址配置不保证相同。
3. 控制地址、HCA 和 GID 的关联缺少核验；显式选择不同网络是合法的，但应能解释结果。
4. `server.py` 固定调用 `register_store("cpu:0")`，把整个槽池标成 NUMA 0。只有实际页位置不符时才构成错误，不能概括为 Mooncake 拓扑表失效。
5. Python 在 preflight 阶段要求控制地址并创建传输后端，C++ 自动选卡若只接在 bootstrap 中，无法覆盖整个启动流程。
6. 缺少区分“发现设备”“允许设备”“实际启用设备”的统一日志。

## 2. 目标与边界

目标：**在本地信息足以消歧时自动选择；显式配置被正确保留；信息不足时给出候选和原因；不依赖 Mooncake 也能运行索引面自动选择。**

- radixshmem 负责公共发现、选择策略、配置核验；后端继续负责建链与传输。发现模块只输出设备信息和选择结果，不持有 QP、MR 或传输会话。
- 索引面、数据面、控制面可以使用不同网络，不要求同卡或同子网。
- 第一版完成本地设备/端口/GID 枚举、访问和有效性检查、HCA 与 netdev/IP 关联、NUMA 信息、启动前配置解析及注册后诊断。
- 第一版索引面限定 port 1，与现有服务端、客户端和 wire 能力一致。其他端口可以枚举展示，但不参与自动选择；若要支持它们，另行补齐配置、发布和连接路径。
- 第一版自动 RoCE 选择覆盖 IPv4 RoCE v2；原生 IB 在链路和 GID 可确认时支持。其他地址族/类型保留受支持的显式配置路径，自动选择范围需在报错中说明。
- 子网与路由是选择提示，不是 RDMA 连通性证明。无法承诺所有部署均零配置启动，也不承诺在建链前识别全部网络故障。
- 不做带宽探测、动态负载均衡、热切换或重写 Mooncake 的调度矩阵。

## 3. Mooncake 已经做了什么

以下是经典 Transfer Engine 的参考行为，入口包括 `topology.cpp`、`rdma_context.cpp`、`rdma_gid_probe.h`；TENT 的接口和策略需单独核对。

| 能力 | Mooncake 的做法 | radixshmem 的接入边界 |
|---|---|---|
| HCA 发现 | 检查设备访问、ACTIVE 端口和 GID 表等 | 候选可用不代表上下文最终初始化成功 |
| 白名单 | 构造参数 filter 与 `MC_TE_FILTERS` 相交 | 适配器应解释显式约束冲突，不能依赖后端静默退化 |
| 拓扑 | 为 `cpu:N/cuda:N` 建立 preferred/available 候选 | 注册位置影响使用哪一行；固定 `cpu:0` 会限制首选集合 |
| GID | 自动排序 RoCE v2/IB 等候选，并保留非零兜底路径 | 索引面的选择结果不代表数据面用了相同 GID |
| 握手地址 | 调用方提供可发布的 host | 地址必须在后端初始化前解析完成 |
| 建链与重试 | 后端建立上下文、连接并执行其重试策略 | 本地发现不能替代跨机建链验证 |
| 设备状态 | 初始化失败可禁用设备，同时保留 HCA 索引 | `getHcaList()` 不能单独作为设备已启用的证明 |

公共模块可以复用同类探测方法；数据面仍由后端执行拓扑调度和 GID 选择。首版统一候选约束与诊断，不声称已接管后端内部所有选卡行为。

## 5. 设计

### 5.1 公共模块与结果表示

建议位置：`src/indexer/transport/rdma/net_discovery.{hpp,cpp}`。系统探测与纯选择函数分开：探测采集 verbs、sysfs、接口地址和路由信息；选择函数只消费已采集数据，便于无硬件测试。

探测可以临时打开 verbs context 查询设备能力，完成后释放；不创建 PD/QP/MR，不保留传输会话。设备名字包含 mlx5 不能替代 DC/XRC 能力检查。编译依赖需保证 `ENABLE_MOONCAKE=OFF` 可用，`ENABLE_RDMA=OFF` 保持既有 standalone 行为。

结果结构至少表达：

```cpp
struct NetAddress {
    std::string address;
    int prefix_length = -1;
};

struct GidEntry {
    int index;
    std::string gid;
    std::string type;
    std::string netdev;
    std::vector<NetAddress> addresses;
};

struct NetDevice {
    std::string name;
    int port;
    bool active;
    bool accessible;
    std::string link_layer;
    int numa_node;
    std::vector<GidEntry> gids;
};

struct IndexPick {
    std::string device;
    int port;
    int gid_index;
    std::string gid;
    std::string netdev;
    std::string reason;
};
```

GID 与关联接口的全部相关地址/prefix 一起保存，不使用 netdev 的“首个 IPv4”代替 GID 对应地址。未知 prefix 使用 -1，不能猜成 /24。以上结构为设计示意，具体类型和字段按现有代码风格落地。

### 5.2 本地选择规则

第一版选卡不依赖自身 rank、rank 0 或尚未发布的 `/peers`。先建立 port 1 上可访问、ACTIVE、GID 合法且满足传输能力要求的候选，再依次处理：

1. 应用所有显式约束。`index_dev` 非空则固定该设备；`gid_idx >= 0` 则固定该设备上的对应索引，即使 `index_dev` 留空也必须应用 GID 约束。显式值无效时直接报错。
2. 经过约束和 GID 选择后，若只剩一个可用组合，直接选择，不要求 registry 出口必须能映射到 HCA。
3. 仍有多个候选时，使用显式控制接口/地址的关联关系作提示；它不覆盖显式 `index_dev`，也不强制控制与索引同网。
4. 仍无法唯一确定时，可查询 registry 路由的出接口和源地址作弱提示。loopback、管理网无 HCA、DNS/路由查询失败或多结果冲突均表示提示不可用，继续消歧/报候选，不据此判定所有 RDMA 设备不可用。
5. 最终仍有多种合理组合时，报错列出设备、port、GID、netdev、地址/prefix、NUMA、过滤原因，要求补充显式配置；不按枚举顺序取第一项。

首版不按速率或 NUMA 给索引候选强行排序；NUMA 信息保留供诊断及数据面拓扑使用。已知 prefix 的子网比较可用于后续诊断；未知 prefix 明确显示 unknown。

### 5.3 启动顺序与控制地址

当前 C++ 先创建 RDMA context，再进入 etcd rendezvous；rank 在注册成员后分配。Python 则在 `_preflight()` 中检查控制地址并创建传输后端。因此需要把公共解析入口放在这些地址依赖动作之前：

```text
读取配置和环境覆盖
  → 本地发现，解析控制地址 / 索引组合 / 数据面约束
  → 将结果保存为统一的运行时配置
  → Python preflight、后端初始化；C++ 创建 RDMA context
  → 发布 /peers、分配 rank
  → 注册后兼容性诊断和正常建链
```

- Python 通过 binding 调用同一解析实现，在创建传输后端前完成解析；修改 preflight 的必填检查和 `resolved_transfer_ip()`，不能在分布式自动模式缺地址时静默退到 127.0.0.1。
- C++ 直接入口也调用同一解析实现。已经解析的选择再核验可用性，不重新套另一套优先级。
- 实际选中的设备和 GID 写回运行时配置，后续 context、`fill_local_entry()`、本机客户端和日志使用同一结果。
- 保留 `rpc_interface` 优先于 `rpc_address` 的现有约定，两者都给出时明确告知生效项。两者都空时，可从选中索引组合关联的有效 IP 推导；多地址无法消歧或接口不可见时要求显式配置。
- 显式控制地址与索引网络不同是合法部署，不自动改写。自动发布地址不能是通配地址；显式 0.0.0.0 的既有单机测试行为单独保留，不作为跨机可达地址。
- 解析后的地址同步用于传输握手、节点身份派生和监控等地址消费者，避免 Python 与 C++ 各持一份不同结果。
- gRPC/XRC 继续沿用当前监听方式；本设计决定发布地址，不新增 socket 出接口绑定语义。

注册后核验覆盖所需 peer 的实例、链路层和地址类型等可确认信息。同子网仅作为提示，不保证 RDMA 可达；不同子网可能经路由可达，不能仅凭网段不同直接拒绝。无法预判的网络故障由有超时的实际建链报告，不把“看见 rank 0”当作全体 peer 可达的证明。

### 5.4 GID 选择规则

`gid_idx = -1` 表示自动；默认值从 3 改为 -1，C++ 服务端/客户端、Python 配置和 CLI 一起调整。

1. 显式索引必须在选中 port 1 上查询成功、非零且与支持的链路/地址类型相容；不回退到另一个索引。
2. 自动 RoCE 模式优先有效的 IPv4 RoCE v2 GID。根据 GID 对应 netdev/IP 与显式地址或可用路由提示消歧；容器里看不到接口时保留“关联未知”，不能凭空生成掩码。
3. 相同 GID 的重复索引可按固定规则去重；不同地址仍有多个合理候选时报告歧义，不能随便选首项。
4. 原生 InfiniBand 按实际 IB 链路和有效 GID 处理，不能把 RoCE 地址匹配失败简单当作可切换到 IB 的理由。无可确认候选时要求显式配置。
5. 每个节点发布自己的实际 GID 索引和原始 GID。远端的索引值不用于本机查表。

第一版索引端口固定 1，因此沿用当前 `/peers` 和 wire 字段。若支持其他端口，需在实现前完成服务端、客户端、配置及协议的端到端设计，不能只扩充发现函数。

### 5.5 数据面与 NUMA 注册位置

公共模块输出允许的设备集合和选择原因；Mooncake/NIXL 继续执行集合内的拓扑调度及 GID 选择。数据面默认候选不等于全部 ACTIVE HCA 都已启用，也不强制跟随索引面同卡。首版不增加按速率筛卡规则。

`transfer_ip` 留空时使用已经解析的控制地址；握手地址与 RDMA 网络可以不同，但都需要满足各自的可达性要求。日志分别显示握手地址和后端设备状态。

NUMA 注册位置作为独立改动验证：

- 去掉 `register_store("cpu:0")` 的硬编码，优先使用已有空 location / 后端自动探测入口；针对实际 Mooncake 依赖版本检查 wildcard 的行为。
- 首尾页在同一节点不能证明整个池均在那里；`"*"` 也不代表后端会精确识别混合 NUMA，经典 TE 可能仅按首页标记整段。
- 覆盖 prefault 开关、页面未驻留、探测权限不足和未知位置的处理，保留明确的回退诊断。
- 真正的混合 NUMA 分段注册及跨 NUMA 流量分配留作后续优化；页面位置探测属于内存注册路径，不放入网卡选择策略。
- 修正 server 的生产注册路径，并审查其他注册调用的意图；测试中用于明确模拟 NUMA 位置的参数不机械替换。

不能按 9 张卡推算 bond 一定占 1/9：首选概率取决于注册位置对应的 preferred 集合、过滤及后端策略。

### 5.6 配置约束与实际启用状态

核验分两层：

| 层次 | 检查内容 | 输出 |
|---|---|---|
| 初始化前配置检查 | 设备存在、可访问、显式允许集合、已知环境变量冲突、协议是否适用 | planned / allowed |
| 后端初始化后状态检查 | 后端可确认的活动设备、有效候选和实际协议 | active / disabled / unverified |

- `transfer_dev` 显式给出时，不允许已知环境约束把它静默缩成子集。Mooncake 构造 filter 与 `MC_TE_FILTERS` 的冲突应在初始化前报错并列出两边。
- `getLocalTopology()->getHcaList()` 只作为发现/索引信息；v0.3.14 禁用失败设备时可能保留其名字，不能用集合相等证明实际启用。
- 后端提供可靠的活动状态接口时读取并核对；拿不到实际 GID/活动设备等信息时标记 unverified，不能把 radixshmem 索引面选的 GID 冒充数据面 GID。
- NIXL 的 `device_list`、`UCX_NET_DEVICES` 等按实际依赖版本和适配器语义核验；可确定的冲突报错，无法确认采用结果时明确标记，不能仅打印日志后宣称验证成功。
- 按协议核验：TCP 模式允许没有 HCA，不能共用“设备集合非空”的断言。若 RDMA 请求发生协议退化，日志必须显示实际结果，不能报告为 RDMA 设备采用成功。

### 5.7 客户端

本机客户端没有显式配置时，继承服务端发布的实际 `index_dev / gid_index`，并校验本机同一网络命名空间里的设备、port 1、GID 和能力。

显式配置优先级在服务端、客户端保持一致：客户端指定 GID 时不得被当前 `self.gid_index != gid_idx` 分支静默覆盖。与本机服务端发布结果冲突时明确报错或按已定义的覆盖语义处理，不静默替换成其他设备/GID。

设备名和 GID index 是本机信息，不能照搬远端 rank 的值。观察者（rank < 0）没有自己的 `/peers` 项，使用第 5.2 节本地规则；已有 peer 信息仅作诊断。不同网络命名空间无法复用服务端选择时，需要显式本地配置。

### 5.8 启动日志

配置解析后记录 control、index 和 transfer 的 planned/allowed 结果；rank 分配及后端初始化后补充实例和实际状态。例如：

```text
[RadixServer] net: control 10.6.131.11 (rpc_interface) | index mlx5_bond_0 port 1 gid 3 (10.6.131.11, bond0, numa 0, control-interface hint)
[radixshmem] MooncakeBackend: transfer devices allowed=all engine=mlx5_0,...,mlx5_bond_0 active=unverified
[radixshmem] SlotTransfer: pool on NUMA 0, registered as cpu:0
```

`reason` 使用实际命中的规则；设备禁用、环境冲突、prefix 未知和只完成配置检查的项目分别说明。活动设备数量只有在后端确实提供证明时才打印为已验证。

## 6. 配置变化

| 字段 | 现状 | 变化 |
|---|---|---|
| `index_dev` | 空 = 第 0 个设备 | 空 = 本地发现和消歧 |
| `gid_idx` | 默认 3 | 默认 -1 = 自动；≥0 始终作为显式约束 |
| `rpc_interface / rpc_address` | 分布式必填 | 本地信息可确定时允许自动解析，否则要求补充 |
| `transfer_dev` | 空 = 后端自选 | 保留策略，统一设备约束及采用状态诊断 |
| `transfer_ip` | 缺省继承控制地址 | 继承已经解析的地址，分布式自动模式不静默使用 loopback |
| 索引端口 | 固定 1 | 首版仍固定 1，并在候选/日志中明确 |

Python、CLI、C++ 入口的默认值和覆盖语义需统一；自动解析在地址依赖组件初始化之前完成。首版无需新增用户端口配置；今后支持多端口时再补齐端到端字段和兼容性。

## 7. 验收

### 7.1 纯选择与配置测试

使用结构化候选数据测试，不要求 verbs 或真实网卡：

1. 显式设备/GID 的正确与错误路径；只给 GID 时仍应用约束；客户端显式 GID 不被服务端静默覆盖。
2. 单候选、多个候选、无候选、未知 prefix、多 IPv4/GID、重复 GID、接口不可见、port 2 ACTIVE 但 port 1 不可用。
3. /27 地址不能因未知掩码被猜成同一个 /24；网段不同也不能直接推导网络不可达。
4. registry 为 loopback、管理网无 HCA、DNS/路由失败时，唯一有效候选仍可选择。
5. 环境变量和显式数据面约束冲突；RDMA 与 TCP 模式使用各自核验规则。

### 7.2 系统探测与启动集成

假 sysfs 只覆盖文件解析；verbs、接口地址和路由查询通过独立测试替身注入。真实设备查询另做集成测试，覆盖访问权限和能力检查。

1. Python 与 C++ 直接入口都在创建 context/传输后端之前完成同一解析；实际结果用于 `/peers`、握手、节点身份和监控。
2. 初始集群为空、各节点同时启动、rank 0 记录不存在、已有集群加入和观察者启动均不依赖提前分配的 rank。
3. 自动选择与显式部署结果一致的前提写入测试环境，不能把选中某个固定名字当作通用通过条件。
4. `ENABLE_MOONCAKE=OFF` 时索引面可用；`ENABLE_RDMA=OFF` 的既有 standalone 路径不受影响。
5. 后端发现列表保留禁用设备时，不能误报全部 adopted；NIXL 和无法读回的状态明确标记 unverified。
6. NUMA 注册覆盖实际依赖版本、prefault 开关及探测失败；混合 NUMA 不宣称已精确支持。

### 7.3 双机验证

A/B 在各自本地规则可消歧时零配置启动，运行 gRPC remote-op、索引面访问和数据传输，与显式配置基线对比。覆盖本机设备命名/GID 索引不同、索引与控制分网、数据面设备过滤等场景。

明确区分“本地选择正确”“跨机诊断提示”“实际建链和数据校验通过”。无共同可达网络时报告候选和有界建链错误，不保证单靠子网信息提前识别所有故障。

## 8. 实现顺序与范围控制

不设 300 行或其他固定代码行数限制。改动范围按职责、兼容性和验收控制，允许为正确接入补齐配置、binding、启动流程和测试。

建议分步交付：

1. 本地探测和纯选择函数，覆盖端口、GID、地址/prefix、能力与歧义。
2. 统一 Python/C++ 启动前解析和客户端覆盖语义，确保发布结果与实际 context 一致。
3. 后端约束检查及活动/未知状态诊断，区分协议和后端版本。
4. 独立修正 NUMA 注册位置并完成相关回归。
5. 双机验证、日志和部署文档。

若实现需要运行中重建 QP、动态迁移流量、跨机协商后重新选卡或改多端口 wire，需单独设计相应生命周期和兼容性后再扩展；代码行数本身不作为停止条件。
